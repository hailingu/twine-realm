# Go 开发规范

本规范适用于平台服务（目标目录 `server/`）的全部 Go 生产与测试代码，与[软件工程规范](software-engineering-standard.md)共同使用。当前 `server/` 尚未建立，本规范约束首批及后续代码。

## 工具链基线

- Go 版本基线为 **1.27**（核实时最新稳定为 1.27.3），以 `go.mod` 的 `go` 指令锁定；本机当前为 1.25.6，初始化工程前先升级，见[运行时与工具链](runtime-toolchain.md)。
- 依赖由 `go.mod` / `go.sum` 唯一定义；不引入无实际消费者的依赖，升级依赖属于明确批准的任务范围。
- 验证命令（初始化 `go.mod` 后生效，当前尚未配置）：`go build ./... && go vet ./... && go test ./...`；`gofmt` 格式必须保持零差异。golangci-lint 接入后以其替代 `go vet` 成为 lint 门禁，见[质量检查](quality-gates.md)。

## 项目布局

```text
server/
├── cmd/platform/       # 平台服务入口：装配依赖并启动，不承载业务逻辑
├── internal/
│   ├── canvas/         # 画布与组件领域模型（纯领域，无基础设施依赖）
│   ├── orchestration/  # 项目空间编排：compose/k8s 适配的端口与用例
│   ├── pipeline/       # AI 流水线：设计-开发-测试-部署的阶段编排
│   ├── runtime/        # 状态采集与调和（期望态 vs 实际态）
│   ├── catalog/        # 标准中间件目录与参数面
│   └── store/          # MySQL 持久化与迁移
└── internal/...适配器  # docker 客户端、DB 驱动、AI 提供商等按端口实现
```

- 包按业务能力组织，`internal/` 下不导出供外部使用的包；`pkg/` 仅在出现真实外部消费者时才允许建立。
- `cmd/` 只做装配：解析配置、构造依赖、注入端口、处理信号退出。
- 目录名即包名，简短、小写、无下划线；不用 `common`、`base`、`util` 类命名。

## 错误处理

- 错误是值：每个可能失败的操作都显式返回 `error`，不忽略、不 `_` 丢弃；跨包错误用 `fmt.Errorf("动作描述: %w", err)` 包装，保留错误链。
- 判别错误用 `errors.Is` / `errors.As`；领域层可定义少量哨兵错误（如 `ErrConflict`、`ErrNotFound`）表达稳定契约，但不得用字符串比较。
- 错误消息用中文描述动作与上下文，小写开头、不加标点结尾；不把敏感信息（凭据、连接串）写入错误。
- 只有不可恢复的内部不变量违反才 `panic`（见工程规范「优先使用断言而非守卫」）；库代码、HTTP 处理器与 goroutine 入口必须 recover 并转为错误/日志，不让 panic 打穿进程边界。
- 失败必须有结果：编排阶段失败返回显式失败状态供上层决策重试或回滚，不返回半成品成功。

## context 与并发

- `context.Context` 是 I/O 承接函数的首个参数，不放入结构体字段（显式传递）；取消信号沿调用链传播，超时设在能决策的层。
- 每个 goroutine 有明确所有者与退出路径：谁启动谁负责停止（`errgroup`、`context` 取消或 done channel）；不启动无人回收的后台 goroutine。
- channel 所有权归一端：发送方关闭，不由接收方关闭；有界任务用 worker pool 或信号量，不用无界 goroutine 蔓延。
- 共享可变状态先考虑消除（改为消息传递或单所有者循环），确需共享时用 `sync` 原语并写明不变量与锁持有范围；不在持锁时做 I/O。
- AI 流水线、编排与调和的每个阶段定义取消、超时、重试与幂等语义；重试不复制非幂等副作用（部署、compose 变更默认视为非幂等，先查询再行动）。

## 接口与依赖注入

- 接口定义在消费方（使用者包内），保持小（1~3 个方法）；不为每个实现预设接口，适配器端口（如 `Orchestrator`、`Provisioner`、`AIProvider`）按测试接缝与替换边界需要引入。
- 依赖经构造函数显式注入，不用全局单例与服务定位器；`cmd/` 装配，测试注入替身。
- 领域包（`canvas`、`catalog` 的领域部分）不 import docker 客户端、MySQL 驱动、HTTP 框架与 AI SDK；外部类型在适配器边界转换为领域类型。

## HTTP API 与序列化

- 优先使用标准库 `net/http`（Go 1.22+ 方法与路径模式路由已满足初期需要）；引入第三方路由框架须在任务内说明必要性。
- API 入参在信任边界显式校验（长度、枚举、引用存在性），校验失败返回 4xx 与机器可读错误码；处理器薄，业务进用例层。
- JSON 字段用显式 tag（`json:"name"`）；时间用 RFC 3339；不依赖结构体默认值的隐式行为表达业务语义。API 契约变更同步更新文档与前端调用方。
- 服务端推送（运行状态回显）优先 SSE；事件带版本与序号，客户端可检测缺口并重新同步到服务端真相。

## 数据库

- 平台元数据 MySQL 经 `database/sql` + `go-sql-driver/mysql` 访问；是否引入 SQL 构建库（如 squirrel/sqlx）在首个持久化任务中决策并记录，不预设 ORM。
- Schema 变更只经 golang-migrate 迁移文件，版本化、可回滚评审；不在代码里做运行时 DDL。
- 事务边界设在应用用例层（对应画布原子提交等不变量），不在仓储方法内隐式开事务；事务内不做远程调用与耗时 I/O。
- 连接串与凭据只经环境变量或配置注入，禁止入库、入日志、入错误消息。
- 画布内业务中间件（项目空间的 MySQL/RMQ 实例）由编排与目录管理，与平台元数据互不混用。

## AI 流水线产物边界

- AI 生成的服务代码、模型变更与 compose 变更进入项目空间前，必须通过与人工代码相同的构建、测试与审查门禁；流水线不得为绕过门禁开特殊通道。
- 生成内容在受控目录构建（隔离的网络与文件系统边界），构建产物与凭据注入由平台执行，不交由生成代码自行获取。
- 流水线阶段间传递结构化的阶段产物（设计、代码、测试结果、部署清单），不传递自然语言夹带私货。

## 测试

- 使用标准库 `testing`，表驱动优先；断言库（如 testify）若引入则全仓统一，不混用多套。
- 领域单测无基础设施依赖；编排与调和的集成测试经真实 docker-compose 边界验证（临时项目空间、明确就绪信号、用后清理）。
- 测试名中文描述场景（如 `Test服务替换_未就绪不切流量`）；不写无断言的测试，不断言实现内部调用顺序。
- 竞争检测：涉及并发的包以 `go test -race` 验证；每个测试文件中时序竞争类用例不超过 6 个，优先表驱动合并同族场景。

## 命名与注释

- 导出标识符 godoc 注释以标识符名开头，说明职责与契约，中文书写；包注释置于 `doc.go` 或该包主文件。
- 命名惯例遵循社区标准：驼峰、不用下划线（测试文件与 `_test.go` 除外）、接口不加 `I` 前缀、错误变量 `ErrXxx`、构造函数 `NewXxx`。
- 常量集中语义命名，不散落魔法数字；单位含在名称或注释中（如 `reconcileIntervalSeconds`）。
