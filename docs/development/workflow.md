# 开发工作流

## 技术方向与当前实现

| 模块 | 当前事实 | 目标方向 |
| --- | --- | --- |
| 平台服务 | Go 项目 / 仓库 / 布局 API | Go：画布领域模型、期望态存储、AI 流水线编排、调和与状态采集 |
| 前端画布 | React / React Flow 本地工作台 | TypeScript + React + React Flow：画布编辑、组件目录、AI 对话、运行状态回显 |
| 元数据存储 | MySQL 迁移、版本与原子回执 | MySQL（平台自身元数据）；业务服务的 MySQL 属于画布内中间件 |
| 项目空间编排 | 未建立 | docker-compose 为本机一等公民，接口按 k8s 可移植设计 |
| 部署 | 未建立 | 服务构建-测试-上线-替换的自动化流水线，零感知替换 |

[平台设计概览](../platform-design/README.md)是目标的唯一入口。当前依赖与命令以实际清单、锁文件与构建配置为准，不能把设计写成已完成事实。

## 目标目录布局

首次建立源码时按以下布局初始化；布局是意向，落地时可在任务内细化，但不得另行发明顶层结构：

```text
server/           # Go 平台服务
├── cmd/          # 可执行入口（如 cmd/platform）
├── internal/     # 领域、应用用例、基础设施适配（不对外包）
web/              # TypeScript 前端（Vite + React）
deploy/           # 项目空间模板、compose 骨架与平台自身部署
docs/             # 文档（platform-design 设计、development 规范）
issues/           # 历史、离线草稿与明确链接的证据快照
```

新增首个受维护源码路径时，必须在同一变更中补充根指南范围路由行与对应工具配置，使新路径实际参与检查。

## 开始任务

1. 阅读根指南、工程规范与适用的平台设计。检查当前分支、工作区与已有能力。
2. 对工作分类（见根指南「变更分类」）；开发变更必须在独立任务分支和 worktree 中进行，先保留已有修改并核对基线，不在 `develop` 直接开发或提交。
3. 读取原 GitHub Issue 与 Project item，核对已接受范围、实际阶段及重复项；明确本次切片的用户入口、领域不变量、服务与数据边界、验证和交付条件。全新平台不代表每次任务都授权全仓搭建或部署。
4. 可复现缺陷先有失败证据再修复；源码功能实现前先记录状态与不变量矩阵。

## 工作记录与看板

具体工作在 GitHub Issue 维护范围、验收、阻塞与实现 / 检查证据，Project #4 管规划、排序与阶段，入口及规则见[Projects 与 Issues 协作](project-tracking.md)。创建前查重，创建后核实原 Issue 已关联目标项目；本地 `issues/` 不另建同项任务的独立状态。

当前 Project 已启用 Done 自动关闭 Issue、Issue 关闭后设为 Done 等工作流。未验收不拖 Done；完成后优先关闭原 Issue，再读取 Project 状态。重开、PR 关联和自动化失败均须检查两处并修正原 item；不把自动化配置、一次请求受理或本地 `issue:status` 通过当作同步成功。

## 状态与不变量矩阵

源码功能或可复现缺陷修复在修改生产代码前，在任务计划、设计文档或变更说明中记录简明矩阵（无需另建文档）：前置状态、动作顺序、预期可观察结果、跨转换不变量与所有者、对应测试或验证缺口。按风险选择场景，不要求穷举。

平台特有的验证方向（不代表用例已存在或通过）：

| 状态或转换 | 应保留的结果 | 主要验证所有者 |
| --- | --- | --- |
| 画布声明与项目空间实际态偏差 | 偏差可观察、可解释，调和收敛后消除 | 调和器与状态采集 |
| 服务替换期间持续有业务流量进入 | 新版本健康就绪后切流量，失败回滚到上一可用版本 | 替换编排与真实 compose 环境 |
| AI 生成服务未通过测试 | 不进入项目空间，画布保持上一版本 | AI 流水线与部署门禁 |
| 共享中间件被多画布同时使用 | 引用计数正确，单画布销毁不影响其他画布 | 中间件目录与生命周期管理 |
| 声明热生效的配置修改 | 立即生效且运行状态如实回显，失败可见 | 配置管理与配置下发链路 |
| 部分失败的编排（如中间件起来了、服务失败） | 持久记录已完成步骤与资源，安全重试 / 补偿或人工处理，不删除保留数据；不要求跨系统整体事务 | 持久操作与编排执行 |
| 画布编辑并发提交 | 原子提交，冲突不覆盖新数据 | 画布领域模型与 MySQL 持久化 |
| 外部步骤完成后响应丢失，平台执行中重启 | 按原操作与资源身份核实，接续一次有效结果，不重复创建 | 持久操作与适配器 |
| 新目标取代旧任务，旧响应迟到 | 旧代次不回写当前版本，不误清理新资源，已有副作用可对账 | 调和器与资源归属 |
| SSE 断连 / 重复 / 过期游标 | 去重重放或完整快照恢复，草稿保留，过期观测明确 | API / 事件与前端会话 |
| 停止、移除和删除失败 | 行为分开，默认保留源码与卷，删除中和残留可见 | 生命周期与清理操作 |
| 每种技术栈接入及 agents 任务启动 | 对应工程文档离线可读，每服务 AGENTS 引用适用规范，加载版本可核实 | 工程方案与 AI 前置校验 |

覆盖正常、失败、取消、重试、乱序与并发等适用路径；不以模拟调用次数替代跨真实边界的验证。

## 实施新系统

- **纵向切片交付**：首个功能为 [Issue #1 本地仓库加入画布并保存](local-project-slice.md)，交付可操作、可持久恢复的行为。业务编排切片再验证真实 compose 与状态回显。
- 后续首个业务运行切片（以数据库版 Todo List 为示例项目）：单画布 + 标准 MySQL + 一个手写 Todo 服务 + 独立本地 Git 最小登记 / 固定 commit 追溯 + 真实 compose 与数据库持久化 + 状态回读。源码与提交可先手工准备，构建必须绑定已验证 commit，不能延后全部 Git 追溯；完整 Git UI、AI 生成、GitHub、零感知替换和配置热生效随后逐片接入。Todo 不成为实际用户项目的业务限制，首个业务语言 / 框架仍待选择。
- 领域模型（画布、组件、期望态、调和）放在 `server/internal/`，不依赖 HTTP、docker 客户端与 MySQL 驱动等基础设施细节；通过接口注入端口实现。
- 前端 React Flow 只做画布投影，服务端持有已提交画布真相；交互预览不直接持久化为业务图。
- 组件定义、具名端口、关系类型与首批机器契约遵循[契约设计](../platform-design/canvas-contracts.md)；标准中间件按[版本化 schema 与运行契约](../platform-design/standard-middleware.md)发布配置、端口和绑定规则，业务迁移仍由服务仓库管理。画布编辑原子性不扩展为 Git、Docker 与业务库的大事务，外部执行按[持久操作与恢复](../platform-design/operations-and-recovery.md)处理。
- 一期不接入账号、配对、会话或 RBAC。Issue #1 只做本机监听、Host / Origin / 路径防护、平台库迁移、只读 Git、版本冲突与原键恢复。业务运行切片再验证服务 commit、MySQL 绑定 / 迁移 / 就绪、运行资源与事件。
- 业务技术栈开放前交付对应的最佳实践文档包、离线快照、模板和实际检查，每服务仓库 `AGENTS.md` 引用适用通用及技术栈规范。agents 开发前实际读取并记录固定版本，平台专属规范不自动套用于业务服务。
- 平台自身的元数据 MySQL 与画布内业务中间件是两个边界：前者由 golang-migrate 管理迁移，后者由画布声明驱动，不得混用。
- AI 产物（生成的服务代码、模型变更）走与人工代码相同的门禁；流水线实现中不得为绕过门禁开特殊通道。

## 验证与同步

- 先运行聚焦检查，再按根指南范围路由运行完整命令；当前无自动检查时做结构化评审并如实报告。
- 涉及项目空间生命周期的功能，至少一项验证经过真实 docker-compose 边界，不能只对编排器 mock 断言调用次数。
- 设计变化同步更新 `docs/platform-design/` 与索引；工程要求留在本目录。工作事实与关闭结论写到原 GitHub Issue，核对其 Project item；`issues/` 仅保留历史、离线草稿或注明权威链接 / 日期的快照。
- 完成前只清理本任务生成的一次性产物，保留用户数据与无关工作。报告真实命令、环境、结果、矩阵覆盖、未完成项与已知限制。

## 版本控制与交付

开发交付必须按 **独立分支 / worktree → 检查与提交 → 推送 → PR 合入 develop → 同步本地 develop → 清理已合并分支 / worktree** 完成。`main` 保留历史与发布边界，`develop` 是集成分支，均不作为直接开发 / 提交的位置。以下动作在用户已授权范围内接续执行；规范本身不授予无关发布、远端写入或数据删除权限。

1. **核对与隔离**：检查 `git status`、分支、已有 worktree、原 Issue 和 Project；读取最新 origin，确认本地 `develop` 与远端关系。干净且无分歧时仅快进同步，不用强推或 hard reset 覆盖差异。保留用户未提交文件；归属不明或基线冲突先报告，不自动混入任务。
2. **创建任务工作区**：从已核对的 `develop` 用 `git worktree add -b feature/<issue>-<slug> <独立目录> develop` 建立任务分支与 worktree，其他类型可用 `fix/`、`docs/`、`chore/`。已存在本任务 worktree 时核对后复用，不能仅因命名重建或清理其他工作区。
3. **检查与提交**：纯文档做结构化评审、链接与空白检查；源码 / 配置按范围路由验证。先用 `npm run hooks:install` 启用真实 Git hook，再执行完整 `npm run precommit`。仅暂存本任务授权内容并审阅 staged diff；Git 提交再次经 hook 检查源码 / 配置与索引一致。告警与依赖漏洞均为零，禁止绕过，详见[零告警提交门禁](warning-free-commits.md)。提交信息使用中文「类型：描述」。
4. **推送与 PR**：推送本任务分支并建立 upstream，不直接推送 `develop`；创建目标为 `develop` 的 PR，关联原 Issue，写明最终行为、验证、已知边界和未运行项。仅完整覆盖验收的 PR 使用完成关联；部分交付只引用原 Issue。
5. **合并屏障**：核对 PR 最新 head SHA 与实际提交、完整本地门禁、PR CI 的每个适用 job、仓库要求的审阅及原 Issue 验收。等待、失败、被取消或尚未运行都不能当作通过；新提交后读取新一轮检查。满足后合并到 `develop`，默认保留 merge commit 便于核实任务提交的祖先关系；仓库限制其他方式时记录实际策略及对应合并证据。不能因本地测试通过而跳过真实 PR CI。
6. **同步集成分支**：读取合并结果并 fetch origin，在原 `develop` worktree 仅快进更新。原目录中已纳入 PR 的改动也须先逐文件核实并保留可恢复副本，不能直接清空；不相关修改保持原样。存在冲突、分歧或归属不明时停止同步并报告。确认本地 `develop`、`origin/develop` 与远端实际版本一致；这不代表已部署。
7. **清理屏障**：先确认 PR 已 merged 且目标为 `develop`，分支 tip 未被他人推进，全部任务提交已包含于集成历史；若采用 squash / rebase，则额外核对 PR 原 head、合并提交与最终文件，不以分支名推断。检查任务 worktree 的暂存、未暂存、未跟踪及忽略文件，保留任何用户数据或未保存成果。
8. **仅清理本任务**：核实后删除 origin 上对应开发分支，正常 `git worktree remove <任务目录>`，再用 `git branch -d <任务分支>` 删除本地分支；不使用强删或强制移除。若删除被未合并检查阻止，保留并报告，不能为完成清理使用 `-D`。保留 `main`、`develop`、未合并分支、其他 worktree、数据库、卷、示例及用户文件，最后重新核对远端 / 本地分支与 worktree 列表。
9. **任务收尾**：把 PR、合并提交、实际检查和剩余边界记录回原 Issue；满足完整验收和合并条件后关闭，再核对原 Project item 为 Done。报告同步与清理结果，无法安全完成的部分明确保留，不把 PR merged、Issue Closed、Project Done 或服务已部署混为同一事实。

质量检查入口与证据见[质量检查与证据](quality-gates.md)。容器构建、预览启停、部署及远端数据操作仍按运维授权处理；开发 PR 合并不等于授权启动业务服务或删除运行数据。
