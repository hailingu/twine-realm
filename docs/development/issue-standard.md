# 问题记录规范

本规范用于缺陷、功能、工程债务与评审处置记录。具体工作以 [GitHub Issues](https://github.com/hailingu/twine-realm/issues) 为权威记录，[Project #4](https://github.com/users/hailingu/projects/4) 管规划、排序和执行阶段；职责、去重、当前自动化及状态修复见[Projects 与 Issues 协作](project-tracking.md)。根 [issues/](../../issues/README.md) 保留已有历史、离线草稿和明确链接的快照，不默认创建同名本地副本。

## GitHub Issue 的创建与维护

- 创建前检索仓库相关 Issue（含 Closed）和 Project item；已有任务复用原记录。已接受的可执行工作必须关联正确 Project，若目标不明确先报告，不只创建未关联的 Issue。
- Issue 保存背景、范围、验收、讨论、实现与检查证据、阻塞原因和关闭理由；Project 引用原 Issue，维护 Status、Priority 和排序。PR / commit 作为实现证据关联，不另建同项任务卡。
- Issue 使用 GitHub 分配的 `#n` / URL，不套用本地 `ISSUE-xxxx` 文件头。功能标题直接描述结果；缺陷仍按下文事实依据说明严重性和范围，未核实标签不自行创建。
- 当前 Project 的 Done 会触发自动关闭 Issue；验收后优先关闭 Issue 再核对 Project。新建 / 关闭 / 重开 / PR 关联均按协作规范验证实际结果，不把自动化配置当执行成功证据。

下列文件名、front matter、日期和枚举约束只适用于本地记录，检查脚本行为保持原样。

## 本地历史与离线草稿格式

- 目录不存在时在当前授权工作区创建。目录导航见 [issues/README.md](../../issues/README.md)，新记录从 [_template.md](../../issues/_template.md) 复制并按问题类型裁剪。
- 文件名采用 `ISSUE-0001-中文短名.md`；`ISSUE-0001` 是稳定编号，从现有最大编号递增分配，不重用已关闭或已删除记录的编号。
- 修改标题、范围或状态时保留编号与文件名。并发创建前后检查编号冲突，冲突在集成前重新分配并更新引用，不覆盖另一份记录。
- 文件头必须包含 `id`、`title`、`type`、`status`、`priority`、`scope`、`createdAt`、`updatedAt`；日期采用 `YYYY-MM-DD`，未确认的负责人可留空，不编造归属。
- `type` 使用「缺陷」「功能」「工程债务」「已知边界」；`status` 使用「待处理」「进行中」「待验证」「已关闭」「暂缓」；`priority` 使用 `P1/P2/P3`，与标题一致。
- 本地状态、级别和范围只表达该历史 / 草稿快照，不能覆盖权威 GitHub Issue。每次本地记录变化更新 `updatedAt` 与处置记录，已经关联远端时同时注明权威链接和核对日期；暂缓不是修复。
- 仓库根 `npm run issue:status` 自动校验文件头必填字段、枚举、编号一致且唯一、日期格式及 `updatedAt` 不早于创建日期和最后处置记录，并输出状态统计与未关闭清单（`--json` 为结构化摘要）；验收与证据质量仍由结构化评审保证，该命令不代替评审。
- 以 `ISSUE-` 开头且以 `.md` 结尾的候选记录先校验文件名格式；编号位数或短名不合规时报错，不从统计中静默忽略。
- 处置日期只从「处置记录」章节的正文和下级日期标题提取，支持 `YYYY-MM-DD：…`、`YYYY-MM-DD（说明）：…` 与 `### YYYY-MM-DD 说明`；遇同级或更高标题结束章节，其他章节和代码示例的日期不参与比较。

## 标题与严重性

本地记录标题采用 `P<1|2|3>(<scope>): <问题摘要>`，例如 `P1(server): 期望态存储写入竞态导致画布漂移`。范围可用 `server`（平台服务）、`web`（前端画布）、`deploy`(部署与项目空间模板)、`design`（平台设计文档）、`docs`（开发规范与治理文档）或 `tooling`（仓库工具与质量门禁），一个问题一个范围；确属跨域的单一记录可用 `+` 联写（如 `server+web`），各段仍须在枚举内。摘要描述问题，不用提交类型代替严重性。

| 级别 | 判断依据 | 处置 |
| --- | --- | --- |
| P1 | 正常操作、常见脏数据或已知行为可导致数据丢失、损坏、泄漏、越权，或核心流程不可用 | 相关任务交付前修复或由所有者明确处置，不得隐去风险 |
| P2 | 触发依赖较窄竞态、罕见数据或边界值，有影响但有可用绕过方式 | 记录触发与影响，修复或明确登记边界 |
| P3 | 无当前可达故障证据的额外加固、文档或工程债务 | 按收益和范围排期，不据假想风险扩大任务 |

平台核心不变量（孪生一致性、零感知替换、声明原子性、凭据隔离、AI 产物不豁免验证、配置生效语义显式）的破坏至少按 P1 评估。严重性必须有可达触发与影响依据，不确定项明确标为待确认，不伪造复现或原因。

GitHub 缺陷严重性在 Issue 正文说明，本地历史 / 草稿沿用 `priority` 字段；Project Priority 是排期维度，不强制与严重性相同。已知边界在记录中明确标识；没有完整调查不妨碍先记录可行动的问题，但未知信息必须明示。

## 内容与验收

缺陷记录依次包含：环境、复现步骤、期望结果、实际结果、证据、回归来源。

- 环境区分分析代码修订与实际运行版本，注明平台、入口和相关配置；未知项如实标注。
- 步骤给出前置状态、动作顺序与观察点，区分用户报告、本地复现和构造示例。
- 证据说明已确认原因与假设，引用稳定提交、符号、脱敏日志、命令结果及可访问截图。已有测试通过不证明缺陷不存在。
- 在证据中列出可验证验收标准，说明触发、可观察成功结果、验证方式及必须保留的行为。
- 回归来源只写已确认的引入提交；调查基线不是缺陷引入版本，无法定位时写明未知。

功能记录包含背景与目标、方案草案、验收标准；未决设计保持为问题，不能编造为已批准需求。已知边界记录包含边界描述、触发条件、现有防线与处置，验收区分「边界已确认」和「实现已修复」。

验收标准应关联状态、不变量与验证，不使用「正常工作」「提升质量」等无法判断完成的措辞。一个 issue 不混入无关问题，证据不包含密钥或不必要的敏感数据；相对链接指向仓库内的稳定文件，临时截图或报告须说明其保存位置与可用期限。

## 评审与关闭

每项实质意见记录「处置、理由与变更、验证、后续」。延期和等待决策不能称为已修复；重复问题可关联同一处置，但应说明适用原因。

进入待审阅 / 待验证阶段时在 Issue 记录实际改动、对应命令和剩余验收。代码完成类关闭前必须完成验收、通过完整门禁与 PR CI、经独立分支 / worktree 的 PR 合入 develop 并核实本地同步，记录提交、PR 与适用检查；清理有安全阻碍时保留并记录，不强删。仅当前工作区通过不等于已交付。无需变更、取消、重复或保留边界的关闭，明确相应理由、证据与权威后续。关闭后核对 Project，误关则重开原 Issue 并修正原卡片。

设计变化同步 [平台设计概览](../platform-design/README.md)。关闭结论形成于权威 Issue，并核实 Project；本地文件只保留已注明来源 / 日期的快照，不删除历史。关闭本身不是提交、合并或部署证据；代码完成类须满足上述交付条件并分别列出事实，非完成类关闭不冒称实现已交付。分支 / worktree 与清理的完整要求见[开发工作流](workflow.md#版本控制与交付)。
