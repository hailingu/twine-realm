# 软件工程规范

本规范适用于平台全部生产源码与测试源码，约束代码结构、职责、依赖、复杂度与验证。本规范约束当前本地切片及后续源码。

根目录 [AGENTS.md](../../AGENTS.md) 定义任务授权、范围路由与版本控制规则。本规范与 [Go 规范](go-standard.md)、[TypeScript 规范](typescript-standard.md)共同适用；公开契约、安全要求及已接受的设计决定优先于实现偏好。发现冲突时先查清权威来源，不静默改写契约。

## 规模与复杂度

规模是检查内聚性的信号，不是机械拆文件的理由。超过评审阈值时，检查职责、依赖方向、状态所有权和独立测试边界。

| 单元 | 分解评审阈值 | 约束 |
| --- | --- | --- |
| 维护的生产源码文件 | 超过 600 物理行 | 不超过 800 行 |
| 维护的测试源码文件 | 超过 1000 物理行 | 不超过 1800 行 |
| 函数、方法、闭包、组件等执行单元 | 超过 60 代码行 | 应当不超过 80 代码行，由评审执行 |
| 可执行逻辑嵌套 | 超过 4 层 | 不超过 6 层 |

文件计完整物理行，包含注释与空行；执行单元从签名到实现结束，注释行不计、空行计。声明式注册表与测试数据表不自动豁免，应说明它们是否仍只有一个责任。当前未接入自动规模检查，不得把人工评审说成自动门禁已通过；超限单元在评审指出时于本次变更内拆分，无关存量问题记录为技术债。

## 职责与模块边界

- 一个模块、包、组件或功能域负责一项内聚能力，名称表达业务责任（画布、组件目录、调和、编排、流水线），避免只有实现技术含义的命名。
- 公共表面保持小而明确。不得仅为测试方便把内部对象、可变状态或辅助函数变成公共 API；Go 中体现为审慎使用导出标识符，TS 中体现为命名导出的最小集合。
- 新模块应明确所有者、输入、输出、不变量、错误与清理责任；公开声明必须在实现体前有表达意图的中文文档注释。
- 一起变化的代码尽量靠近；禁止靠移动行数制造形式上的模块化，也不向 `utils`、`helpers`、`common` 等目录持续堆放无关能力。

## 注释与文档

- **语言**：所有注释使用中文，包括文档注释、行内注释、分隔注释与 TODO；工具要求的固定标记（`@param`、license 头）不属于注释内容。
- **文档注释**：新增公共文件、包、模块、类型、函数、组件与方法在实现体前有表达意图的中文文档注释，说明职责、契约（参数、返回、错误、清理）与边界，不复述实现步骤。Go 按 godoc 惯例（`// 注释`置于声明前），TS/TSX 采用 TSDoc 风格并补全 `@param`、`@returns` 标签。
- **行内注释**：解释「为什么」与约束来源（设计文档、契约、issue 编号），不复述代码字面；与代码冲突的过期注释在实质修改时一并修正。
- **分隔注释**：可用简短中文分隔注释组织长文件区域（如 `// ── 区域名 ──`），不得以分隔注释代替职责拆分。
- 不提交被注释掉的代码；TODO 必须写明背景与跟踪入口（issue 或任务）。

## 依赖方向

- 前端与基础设施适配器依赖稳定的应用或领域契约；领域规则（画布、期望态、调和语义）不依赖 HTTP、docker 客户端、MySQL 驱动、React 或浏览器 API。副作用经显式注入的端口进入领域层。
- React Flow 是画布投影层；节点、边与位置变化经领域用例提交到服务端，不能在前端建立另一套可独立写入的业务真相。
- 共享契约放在明确归属的叶模块；维护模块不得形成循环依赖（Go 包依赖、TS 模块依赖与 `import type` 同样受限）。
- **不保留无实际使用的引用**：新代码不引入未使用的导入、变量、类型与依赖；能力移除后，不再有任何实际消费者的清单依赖随该变更一并清理。
- 在信任边界（HTTP API 入参、AI 流水线产物、docker/DB 适配器返回、前端收到的服务端事件）校验外部输入，再转换为领域类型；禁止让外部响应结构成为全仓默认模型。

## 抽象与设计模式

从能保护必要边界的直接设计开始。只有已出现真实变化、独立生命周期、外部 I/O、可复用策略或必要测试接缝时才引入抽象。

| 方法 | 适用问题 | 应避免的用法 |
| --- | --- | --- |
| 端口与适配器 | 隔离 docker 客户端、DB 驱动、AI 提供商等外部依赖 | 只改字段名却继续传播外部语义 |
| 显式状态机 | 服务替换、编排、AI 流水线等有约束转换的生命周期 | 在多个处理函数散落互相矛盾的状态判断 |
| 领域或应用服务 | 不自然归属于单个实体的规则或编排 | 建立容纳所有用例的巨型管理器 |
| 仓储 | 隔离聚合持久化与领域集合语义 | 给每张表包装一层只透传 SQL 的类型 |
| 事件 | 多个独立消费者需要跨异步边界通知 | 未定义顺序、重复、失败语义便替代直接调用 |
| 工厂或构建器 | 构造按类型变化或必须保护多个不变量 | 为单个固定构造增加层次 |

优先组合与显式委托；接口归消费边界所有（Go 接口定义在使用方），不为每个具体类型机械创建接口。共享提取通常需要至少两个语义一致且预期共同演进的真实消费者。

## 状态、并发与失败

- 每项可变状态有一个所有者，转换显式、可校验；画布期望态的真相在服务端与 MySQL，前端只持有快照与待提交操作。
- 副作用在 API 与调用位置可见；领域计算尽可能确定且可重复。
- 引入并发前先定义取消、超时、重试、幂等、乱序与部分成功（Go 侧见 [Go 规范](go-standard.md)，前端异步见 [TypeScript 规范](typescript-standard.md)）。重试不能复制非幂等副作用。
- 明确响应成功的提交屏障：画布变更、部署结果与状态回写必须在持久化完成后才报告成功。
- 在能补充上下文或决定恢复的层处理错误，保留原始原因（Go 用 `%w` 包装，TS 用 `cause`），避免每层重复记录同一错误。
- 失败必须有明确结果或可见反馈；禁止静默吞掉错误、丢弃 Promise 拒绝或把失败伪装成空成功。
- **优先使用断言而非守卫**：按当前契约不可能出现的内部状态，用断言在最近位置失败并写明被违反的不变量；不为「不可能情况」编写防御性守卫掩盖缺陷。守卫只用于信任边界的外部输入校验、用户可观察的失败分支，以及并发与恢复路径中按设计允许的竞争结果。

## 测试与变更设计

- 可复现缺陷先提供失败测试或日志证据再修复；源码功能应配对应行为测试。纯文档改动做结构化评审。
- 测试验证可观察行为与稳定契约，不绑定私有调用顺序、实现布局或普通文案；不得把仓库源码或文档当不透明文本断言措辞、出现次数、行数或章节位置。
- 风险属于编排、事务、并发、docker 边界或资源所有权时，至少一项验证经过真实生产边界或行为等价的集成装置；只断言 mock 被调用，不能证明跨组件、存储或容器边界的结果。
- 需要真实 docker、MySQL 或网络的测试应隔离临时资源、使用明确就绪信号并保证清理；不以任意等待代替可观察完成。
- 性能优化保持同一行为与验证范围，比较相同条件下的多次结果；不能只删除边界场景或放宽超时就宣称问题已解决。
- 拆分模块必须同步调整测试、公共入口与依赖方向；复用语义适合的组件、schema、错误类型与夹具。

## 渐进采用与例外

新代码立即遵守强制规则。首个切片没有存量迁移例外；后续存量债务不批量重写，实质修改时优先处理本次触及的边界与规模问题，无关债务记录路径、符号与原因（记入 `issues/`）。

对允许例外的规则，记录规则、受影响符号、测量值或结构条件、保留原因、风险、补偿验证与复查条件；不能用例外记录普遍豁免。规范不引入额外提交、推送、部署或外部发言授权。
