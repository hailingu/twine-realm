# 质量检查与证据

本文定义平台的检查现状、计划接入的门禁与完成证据的口径。**核心原则：报告只列实际运行的命令与真实结果；未配置的检查如实说明，不得虚报、不得臆造命令、不得复用历史绿色结论。**

## 当前状态（2026-11-03）

仓库尚无 `server/`、`web/`、`deploy/` 源码与构建配置，Go / TS / compose 检查未配置。**仓库工具与质量门禁已建立**：根 `package.json`（Node 24.18.0 / npm 11.16.0，`.nvmrc` 锁定）承载下列已接入命令，全部在仓库根执行：

| 范围 | 命令 | 说明 |
| --- | --- | --- |
| 工具脚本行为测试 | `npm run test:quality` | 原生 Node 测试覆盖 Sonar 门禁、完整门禁编排与 issue 状态检查，涵盖失败传播、报告隔离与凭据脱敏 |
| issue 元数据与状态 | `npm run issue:status` | 解析 `issues/` 文件头并校验必填字段、枚举、编号唯一与日期一致，输出状态统计与未关闭清单（`--json` 结构化摘要）；能证明元数据合法与状态如实报告，不证明验收与证据质量，未关闭记录不构成失败 |
| 单独 Sonar 复核 | `npm run sonar` | 只扫描与核对本次分析；不自动复用本地覆盖率报告，不替代完整门禁 |
| 完整质量门禁 | `npm run quality:gate` | 依次执行原生脚本测试（同次采集 `scripts-lcov.info`）、issue 元数据校验，并把本次 LCOV 传给真实 Sonar Quality Gate；前置检查失败立即停止，临时目录成功或失败后清理 |

除上述自动检查外，文档与规范变更仍做结构化评审：核对一致性、路径与链接、真实命令描述、适用范围和未完成事项。

## Sonar 门禁

项目标识为本地 SonarQube（社区版 26.8，docker 于 `localhost:9000`）已建立的 `twine-realm`，由根目录 `sonar-project.properties` 维护。当前扫描范围是维护脚本 `scripts/`（生产 `.mjs` 与测试 `.node.mjs` 按配置分类）；`server/`、`web/`、`deploy/` 建立后同步扩展 sources 与对应分析参数。平台无 Java 源码，扫描器不传 Java 字节码参数；适配器保留该能力，在提供构建目录时要求产物真实存在。

- 本地终端从 `~/.zshrc` 加载 `SONAR_HOST_URL` 与 `TWINE_REALM_SONAR_TOKEN`，也支持专用于本次运行的 `SONAR_TOKEN`。凭据只经扫描器环境与 API 认证头使用，不放入命令行、配置文件或报告；诊断输出自动脱敏。无凭据或服务不可达时门禁失败，不得输出 shell 配置全文。
- 扫描器等待服务端 Quality Gate（默认 Sonar way），再按本次任务的 analysisId 确认结果为 `OK`；任务、项目、报告、HTTP、状态不明或扫描失败均返回非零。不采用项目上一次绿色结果，不放宽服务端门槛。默认等待 300 秒，`SONAR_GATE_TIMEOUT_SECONDS` 可设 1–3600 秒；扫描器可通过 `SONAR_SCANNER_BIN` 指定（本机 sonar-scanner CLI 7.3.0）。
- 覆盖率结论须核对采集范围与服务端实际分析：完整门禁只导入本次临时目录的真实 LCOV，缺失报告拒绝扫描，不回退历史 `coverage/`。2026-11-03 首次扫描（分析 `9edb59eb-733b-41f0-b21b-f65d3abe2e63`）conditions 为空，属建立初始基线，不冒充覆盖率达标；随后含覆盖率导入的完整门禁（分析 `97faa9c8-5ec5-4612-b95d-934debe35cc6`）返回 `OK`，`new_violations=0`。未调整服务端门槛，新代码周期实际生效范围由服务端配置决定。
- 纯文档提交（规范、Agent 指南与 issue 记录）只需结构化评审、链接与空白检查，不要求通过 SonarQube 门禁。包含源码或配置（含 `scripts/`、`package.json`、`sonar-project.properties`）的变更须通过适用检查与完整门禁；混合变更不能按纯文档豁免。

## 计划接入的门禁

以下门禁在对应工程初始化任务中接入，并同步扩展 `quality:gate` 编排步骤；接入前它们是目标，不是事实。接入后须同步更新本文与根指南范围路由。

| 范围 | 门禁 | 接入时机 |
| --- | --- | --- |
| Go（`server/**`） | `gofmt -l`（零差异）、`go vet ./...`（或 golangci-lint 接入后替代）、`go build ./...`、`go test ./...`（涉并发包加 `-race`） | 初始化 `server/go.mod` 时 |
| TS（`web/**`） | `tsc --noEmit`（严格配置）、ESLint、Vitest、`vite build` | 初始化 `web/package.json` 时 |
| 涉及项目空间编排的功能 | 至少一项经真实 docker-compose 边界的集成验证 | 首个编排切片 |
| compose / 部署文件 | `docker compose config` 校验 | 建立 `deploy/` 时 |

## 证据与报告口径

- 报告包含：实际运行的命令、工作目录、环境版本、结果摘要、未运行项与原因。
- 优先使用稳定证据：提交号、符号、标题、命令输出摘要、Sonar 任务与分析标识；可变行号仅作辅助。
- 完成的判定标准：请求的行为、必需的文档、必需的检查与必需的证据全部就绪——而非仅仅完成一次实现尝试。
- 跳过、受阻或失败的检查连同完整原因一并报告；凭据缺失、环境故障不能绕过门禁，如实报告即可。
- 纯文档变更做结构化评审与链接检查，不要求运行源码门禁；混合变更不能按纯文档豁免。

## 禁止事项

- 禁止把目标门禁（如「计划接入 golangci-lint」）描述为已执行。
- 禁止以构建成功替代类型检查、以单测通过替代集成验证、以 mock 调用断言替代真实边界结果。
- 禁止为通过检查降低断言强度（删除边界场景、放宽超时、更换更轻替身）后宣称问题解决。
- 禁止复用历史覆盖率或上一次绿色 Sonar 结果作为本次门禁证据；禁止把模拟替身输出当作真实 CLI 证据。
