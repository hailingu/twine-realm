# AI 开发的项目规范与 AGENTS 引用

> **状态：设计方案，未实现。** 强制设计要求：每种受支持技术栈提供对应工程最佳实践文档，每个项目与独立服务仓库 `AGENTS.md` 显式引用适用规范；agents 每次开发任务前实际加载，并记录固定版本、离线快照及读取结果。本轮只更新设计，不改写现有 `AGENTS.md`、工程标准或业务项目，不代表自动加载能力已经实现。

## 强制要求与目标项目

- 对实现、修复、重构、测试和工程配置等 AI 软件开发任务，规范上下文就绪是进入方案分析与代码修改的前置条件；新任务、续办任务及目标范围变化都要重新核对，不能只在首次对话读取一次。
- 每个项目与独立服务仓库的 `AGENTS.md` 必须有可解析的适用通用工程规范与技术栈最佳实践文档引用。引用须关联明确的文档身份、版本与适用范围，任务执行时实际可读；只写「遵循最佳实践」、文件标题或未核对的链接不满足要求。
- 当前已有的文档来源是[软件工程规范](../development/software-engineering-standard.md)。业务项目引用其受控项目适用版本时，必须保留该来源与版本关系，同时读取业务项目自己的现有规范；[技术栈规则集](service-engineering.md)用于补充，不能取代这些文档。
- 「目标项目」由本次任务明确的项目、服务、源码仓库和受影响路径确定；修改平台自身代码与开发用户业务服务分别识别，不能根据聊天中的「当前项目」或进程工作目录自行混用规范。

一个画布项目有项目级规范入口，各业务服务又有独立 Git 仓库中的代码项目入口。项目级与服务代码项目根 `AGENTS.md` 都必须引用已登记的软件工程规范；多服务任务分别发现各仓库及路径级规范，不能用一个服务的入口覆盖其他服务。

| [TypeScript 规范](../development/typescript-standard.md) | 平台 `web/` 与 TS 工具脚本；其中 React / React Flow 要求按原有范围适用 |
| [开发工作流](../development/workflow.md) | 任务分类、切片、状态与不变量矩阵、验证和文档同步 |
| [质量检查与证据](../development/quality-gates.md) | 实际已接入的检查、尚未配置的检查、真实结果与证据边界 |

上述平台规范的原有范围保持不变。业务项目采用[服务工程方案](service-engineering.md#每种受支持技术栈的工程最佳实践文档)发布的受控文档包：逐项映射业务通用条款，绑定所选语言 / 框架 / 场景的最佳实践及项目覆盖项；平台专属 Go、React、目录布局与工具命令不自动纳入。发布包保留来源、版本、适用范围与内容摘要，服务仓库保存不可变离线快照；逐条条款映射和发布工具仍待实施，不因机制已定义就声称业务基线已发布。适用版本或范围无法确认时仍阻塞，不用通用知识替代。

业务项目已有的根 / 路径级 `AGENTS.md`、工程标准、开发工作流和验证说明也必须按任务范围发现并读取。平台文档与业务文档分别标注来源、所有者和范围；同名文件不自动视为同一规范。

## 项目初始化与已有项目接入

| 场景 | 强制设计行为 |
| --- | --- |
| 新建项目 | 在软件开发 AI 任务开始前，由受控初始化流程建立项目 `AGENTS.md`，引用已登记的软件工程规范及可读的受控版本，核对来源、范围和解析结果；不能让 AI 在缺少规范时凭通用知识临时编造一份基线 |
| 新建服务代码仓库 | 仓库根 `AGENTS.md` 显式引用适用通用规范、所选技术栈最佳实践及服务特有文档，核对对应包版本；独立检出或进入隔离工作区后仍可离线读取与核对 |
| 已有项目缺少入口或引用 | 先只读报告缺少的文件 / 引用和影响，提出可审阅的补充方案；不因扫描到缺项就覆盖或重写已有 `AGENTS.md`，接受规范变更后再校验 |
| 已有项目已有规范 | 保留已有内容与未提交改动，逐项核对引用和适用范围；新增共享基线或发现冲突时作为显式规范变更处理，不用模板覆盖项目约定 |

项目级入口与引用版本由项目元数据登记；服务入口和可复现的规范快照随各自 Git 管理，不因此增加一个项目级 Git 仓库。原始规范保持明确的权威来源，副本须可核对来源与内容摘要；不能依赖开发者机器上的绝对路径、不可达链接或未经确认的旧副本。

文档包的组成、不可变发布与仓库内快照原则已固定，推荐服务 `docs/engineering/` 保存文档并由根 `AGENTS.md` 用相对路径引用；具体清单 schema、路径和解析格式随首次实现确定。受控版本不可用时不能将其视为已读取。当前 twine-realm 根 `AGENTS.md` 已有引用，只能证明该文件中的引用存在，不能证明平台已经具备自动发现、加载与阻塞机制。

## 每次任务开始前的发现与读取

1. **确定范围**：明确项目、服务、仓库身份、基准 commit、工作区与拟修改路径。目标不明确时先报告，不猜测应使用平台规范还是某个业务服务规范。
2. **发现入口和引用**：解析服务已接受的技术栈 / 文档包绑定，读取项目与服务仓库根 `AGENTS.md`，按受影响路径发现更具体入口，解析适用通用规范、技术栈 / 框架主文档、验证说明和项目补充。文档集合须与所选组合匹配，不能只读平台语言规范或规范索引。发现范围限于登记的工作区与规范来源。
3. **实际读取适用内容**：检查引用是否指向预期文档、是否可读、内容是否完整、来源版本和范围是否明确。长文档可以分段读取；未读部分、过期摘要和工具截断不能记为已读。
4. **固定规范上下文**：记录每份文档的来源仓库 / 发布标识、路径、版本 / commit、内容摘要（digest）、适用路径和读取状态。存在未提交修改时记录实际工作区内容摘要与差异，不能只读 Git HEAD 后声称采用当前文档；语义摘要不能替代原文读取与内容核对。
5. **建立任务约束与验证映射**：将适用条款关联到计划、代码路径和验证方式。例如职责与依赖边界、规模评审、中文意图注释、状态 / 失败 / 清理责任、行为测试和真实边界证据，均从已读取的源文档版本提取，不在设计中复制另一套可独立漂移的标准。
6. **判定是否就绪**：必需文档均已读取、引用与范围明确且冲突已处理后，才进入业务方案分析、生成或修改代码。缺项时允许只读定位与形成补充方案，不跳过前置条件继续开发或部署。

规范缓存只在来源身份、已接受版本与内容摘要均匹配时复用，并如实记录来源；每次任务仍须读取适用内容、核对当前绑定，不能复用上一任务的「已读」标签，也不能因引用不可读而沿用无法核对的缓存。切换服务、增加修改路径、更新仓库版本或继续中断任务时，重新检查适用集合与内容是否变化。

平台执行器在所有 agents 开发入口统一完成解析和原文加载，并记录文档身份、目标 agent / 任务及读取状态，不能只靠提示词里要求「记得读 AGENTS.md」。多个 agents 参与同一已授权任务时，各自按受影响范围实际取得同一版本的适用规范；这不是要求平台默认启用多 agent 并行。平台外手工启动的 agents 不在自动核实范围，不伪报其已读取。

任务固定使用开始时接受的规范快照。上游发布新版本不改变进行中的任务；服务主动升级绑定、修改适用文档或改变目标范围时，才使相关上下文过期并重新解析 / 验证。离线使用身份、版本和摘要均匹配的仓库内快照属于正常读取，不要求实时联网检查上游；缺少必需快照时阻塞依赖任务。文档可离线不代表模型、依赖安装与构建已经离线可用。

服务采用标准中间件时，agents 同时取得所绑定定义包的配置、端口、连接 schema 与受信运行能力说明，用它们提出候选变更和执行同一领域校验。中间件 schema 不能替代技术栈工程文档或服务自己的接口契约，也不能授予迁移 / 编排权限；业务表结构仍由服务仓库迁移文件负责，见[中间件与运行契约](standard-middleware.md)。

## 执行、验证与变更控制

- 分析和实现阶段使用已固定的规范集合，保留「条款 → 受影响边界 / 实现选择 → 验证或人工审阅」映射；把文档附到提示词末尾不等于已经履行工程要求。
- 人工与 AI 修改使用相同项目规范、技术栈方案和检查入口。自动检查执行源规范与实际配置要求的适用命令；未配置的检查、架构判断和规模评审等人工项如实列出，不虚报自动通过。
- 验证前及准备交付时再次核对规范身份和摘要。规范、`AGENTS.md` 引用、适用范围或目标路径发生变化时，暂停后续变更与交付，重新解析上下文并重做受影响的分析 / 检查；保留已有工作与历史证据，不用旧结果冒充当前结果。
- AI 不得通过删除引用、改写工程标准、降低规则级别或排除检查来消除失败。确需修改规范时，必须作为明确范围的规范变更单独呈现差异、来源和适用影响，不能夹带在功能修改中自我批准。
- 引用存在、读取成功、条款满足与检查通过分别记录。读取记录不能证明模型已正确遵循全部规范，最终仍需实际检查与适用人工审阅。

[简单代码编辑器](code-editor.md)可以定位已登记的规范与引用问题；AI 任务只使用明确绑定的已保存源码 / 规范快照，未保存缓冲区不能冒充当前工作区内容。人工保存服务 `AGENTS.md` 或工程文档、接受 AI 规范变更后，必须重做对应来源与摘要校验；已有任务不能继续沿用旧的「规范就绪」状态。目录浏览与多标签编辑入口不扩大 AI 权限，也不绕过缺失规范时的开发阻塞。

## 冲突处理与不可信内容边界

平台安全边界、任务授权和用户明确的任务范围保持原有优先级。已接受的项目规范与路径级要求先按其范围解析，业务契约、兼容性和强制条款需要同时满足；技术栈规则与模板默认只能在项目规范允许的范围内补充。来源、层级或范围不能确定的冲突必须报告并阻塞，AI 不静默选择更宽松版本。

文档路径、引用和仓库内容都要经过受控解析。普通 README、日志、issue、代码注释、第三方依赖或检索结果默认是数据 / 参考，不因自称「最高规范」就获得指令权；只有经登记并确认来源与适用范围的内容才纳入项目规范集合。即使是项目 `AGENTS.md`，也不能授予读取凭据、跨项目写入、额外联网、安装、推送或部署等未授权能力。

引用不能突破允许的仓库 / 规范包路径边界，不能通过绝对路径、路径跳转或符号链接读取其他项目和敏感文件。文档内的命令不直接执行，只能调用当前任务已授权且受控执行器允许的检查入口；危险或越权指令作为异常内容报告，不混入更高权限的提示或工具参数。

## 阻塞反馈与可追溯记录

| 情况 | 结果与反馈 |
| --- | --- |
| 缺少 `AGENTS.md` 或规范引用 | 标记「规范引用缺失」，指出项目 / 服务和所缺入口，停止软件开发写入与交付 |
| 文档不可读、引用错误、读取不完整 | 标记具体读取失败与目标路径，不生成虚构摘要或回退到一般最佳实践 |
| 来源版本、业务适用条款或规则冲突未明确 | 标记「规范范围 / 冲突待处理」，列出相关来源及待明确问题，由规范所有者处理 |
| 执行期间规范发生变化 | 保留已有工作与旧证据，标记上下文过期，重新校验后再决定受影响操作 |
| 文档包含越权指令 | 拒绝对应指令并记录边界原因，不扩大任务权限，不暴露凭据内容 |

任务记录关联项目 / 服务及仓库、根与路径级 `AGENTS.md` 的路径和摘要、软件工程规范及其他文档的来源与版本、未提交状态、适用条款、读取状态、冲突 / 接受记录、验证映射与实际结果。最终关联源码 commit、工程方案、构建与部署记录；规范上下文不成为另一份可独立改写画布真相的配置。

工程规范加载不授予命令执行、网络或外发权限；任务工具、工作区、预算和凭据由受信执行器控制，具体见[AI 授权与隔离](operations-and-recovery.md#ai-授权隔离预算与数据外发)。

画布与 AI 面板显示规范就绪状态、已读取文档摘要、来源 / 版本和阻塞原因，详情可展开查看。完成报告区分已读、未读、未运行、工具错误与人工待审阅项，工程规范状态独立于服务运行健康。

## 后续验证与待明确事项

以下是未来验收方向，本次没有运行这些产品功能验证。

| 场景 | 预期结果 |
| --- | --- |
| 新项目与独立服务仓库初始化 | 各自 `AGENTS.md` 引用可核对的工程规范，隔离检出后仍可读取，之后才允许 AI 开发任务 |
| 既有项目缺少引用 | 只读报告与补充方案可见，不擅自改写已有入口，不继续代码生成 |
| 项目文档与通用技术栈规则有差异 | 按来源、范围与已接受层级处理，不能用 Google / Alibaba 或 TS 默认替代项目强制规范 |
| 规范有未提交修改或在执行中变化 | 记录实际内容与版本差异，旧上下文不继续作为当前交付依据 |
| 多服务任务各有不同规范 | 分别读取、按各自路径适用，共享基线版本可追溯，不串用另一个服务的规范 |
| 引用指向越界路径或文档夹带越权要求 | 校验失败可见，不读取敏感文件、不增加工具权限 |
| 所选技术栈文档缺失，或只有通用语言风格文档 | 未就绪，不以不完整文档宣称框架组合已支持 |
| 离线但存在同版本、同摘要规范快照 | 实际加载原文并记录来源，不因源网站离线改用其他版本 |
| 多个 agents 参与同一任务 | 各自取得适用固定版本，加载记录可查；读取成功仍不等于全部条款已符合 |

业务共享基线的通用 / 平台专属条款映射、包与引用 schema、发布 / 解析工具及前置校验结果契约仍待实施细化；按技术栈提供文档、不可变离线快照、每服务引用与逐任务实际加载的原则已明确。来源与适用范围不明时按本设计阻止开发。现有工程标准与 `AGENTS.md` 保持原文，不能把本方案描述为已实现的规范加载或门禁能力。
