# 平台设计概览

> **状态：设计意向。** 本文描述平台的目标形态与核心概念。除文档本身外仓库尚无任何实现；所有能力均未建成，各概念以首个纵向切片落地时为准细化。

## 愿景

数字孪生的软件定义平台：**画布即系统**。用户在网页端以类 UML 图的方式在画布中编排组件，平台把画布声明变成真实运行的业务系统，并把真实运行状态回显到画布，形成业务系统的数字孪生。

以「订单发券」项目为例的期望使用场景：

1. 用户创建一张画布，从标准中间件目录拖入 MySQL、RabbitMQ 等作为项目基础组件。
2. 拖入一个通用服务组件，与平台 AI 对话：说明该服务的输入是什么、要处理的业务场景（如「接收订单事件，满足条件则发券」）。
3. AI 完成**数据模型设计 → 开发 → 测试 → 部署**的全流程；AI 判断需要某标准中间件（RMQ、MySQL 等）时，自动将其拖入画布并与当前服务建立关联。
4. 每次与 AI 交互产生的功能改动，由 AI 自动完成开发-测试-上线并**替换现有服务，业务流程零感知**。
5. 画布内实时展示每个服务的真实运行状态；用户可修改服务配置，能立即生效的配置立即生效。

## 核心概念

| 概念 | 定义 |
| --- | --- |
| 画布（Canvas） | 用户编排组件的可视工作区，同时是**一个真实项目空间**的期望态声明。一个画布对应一套 docker-compose（本机环境）/ k8s（规模化环境）项目空间。 |
| 项目空间（Project Space） | 画布声明的运行载体：一组相互关联的服务实例与中间件实例，拥有独立网络、卷与生命周期。 |
| 标准中间件（Standard Middleware） | 平台目录化提供的通用组件（MySQL、RabbitMQ、Redis、Kafka 等），有标准的参数面、健康检查与连接凭据模型。 |
| 服务组件（Service Component） | 由 AI 生成并维护的业务服务；声明输入契约、业务场景、依赖的中间件与对外接口。 |
| 期望态 / 实际态 | 画布及其组件声明构成**期望态**；项目空间内真实运行状况构成**实际态**。平台以调和（reconcile）方式持续收敛实际态到期望态，偏差显式呈现。这是「数字孪生」的一致性基础。 |
| 共享中间件 / 项目中间件 | 中间件可以是全局共享实例（多个画布复用），也可以专属某个项目空间。归属在画布声明中显式建模。 |

## 关键不变量

以下不变量是平台一切实现与评审的最高判据，细化与阶段化见开发规范[开发工作流](../development/workflow.md)的状态与不变量矩阵。

1. **孪生一致性**：画布期望态与项目空间实际态的差异必须可观察、可解释，且只有经平台发起的调和可以消除差异；不得出现画布外漂移的运行组件。
2. **零感知替换**：服务替换期间业务流程不中断——新版本健康就绪后才切流量，旧版本按序下线；失败必须可回滚到上一可用版本。
3. **声明原子性**：画布编辑以原子事务提交；部分失败的编排不留悬空组件。
4. **凭据隔离**：中间件连接凭据由平台按声明注入，不进入画布数据、不入前端、不落 AI 对话记录。
5. **AI 产物不豁免验证**：AI 生成的服务代码与模型变更必须通过与人工代码相同的测试与部署门禁，才可进入项目空间。
6. **配置生效语义显式**：每项服务配置必须声明生效模型（立即生效 / 需重启 / 需替换），平台按声明执行并如实回显。

## 目标架构（分层意向）

| 层 | 技术栈 | 职责 |
| --- | --- | --- |
| 前端画布 | TypeScript + React + React Flow | 画布编辑、组件目录、AI 对话入口、运行状态回显；画布是服务端期望态的投影，不持有业务真相 |
| 平台服务 | Go | 画布与组件的领域模型、期望态存储、AI 编排（设计-开发-测试-部署流水线）、服务注册与配置管理、状态采集与调和 |
| 编排执行 | Go + docker-compose / k8s | 项目空间生命周期（创建、变更、替换、销毁）、零感知替换的流量切换与健康检查 |
| 元数据存储 | MySQL | 画布声明、组件目录、版本历史、运行状态快照 |

## 边界与暂不承诺

- 本机环境以 **docker-compose** 为一等公民；k8s 是规模化方向，接口按可移植设计，不提前实现。
- AI 的自主边界：AI 可以自动引入标准中间件、生成服务代码、执行部署流水线；对**平台自身运行环境**的变更（升级平台、清空数据）不属于 AI 权限。
- 多租户、对外 SaaS 化不在初期范围；先以单用户本机环境打通闭环。
