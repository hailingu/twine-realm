## 愿景

数字孪生的软件定义平台：**画布即系统**。用户在网页端以类 UML 图的方式在画布中编排组件，平台把画布声明变成真实运行的业务系统，并把真实运行状态回显到画布，形成业务系统的数字孪生。

以「订单发券」作为后续扩展场景的期望使用方式：

1. 用户创建一张画布，从标准中间件目录拖入 MySQL、RabbitMQ 等作为项目基础组件。
2. 拖入一个通用服务组件，选择该服务的技术栈与受支持版本、工程规则方案，再与平台 AI 对话：说明该服务的输入是什么、要处理的业务场景（如「接收订单事件，满足条件则发券」）。
3. AI 完成**数据模型设计 → 开发 → 测试 → 部署**的全流程；AI 判断需要某标准中间件（RMQ、MySQL 等）时，把新增组件及关联纳入待审阅变更。
4. 功能改动通过变更审阅或用户明确授权的自动化策略，以及相同的测试与部署门禁后，由流水线**替换现有服务，业务流程零感知**。自动化授权的粒度与默认策略仍待细化。
5. 画布内实时展示每个服务的真实运行状态；用户可修改服务配置，能立即生效的配置立即生效。

AI 软件开发必须先满足[项目规范前置校验](ai-development-standards.md)：每个项目及独立服务仓库的 `AGENTS.md` 必须显式引用适用的通用工程规范和所选技术栈最佳实践文档，每次 agents 任务实际读取并记录固定版本。文档随工程方案发布并可离线读取；通用技术栈规则不能替代项目规范，平台专属条款不自动套用于业务服务。引用缺失、不可读或适用范围 / 冲突未明确时，不进入代码修改与交付。这是目标约束，当前尚无对应实现。

AI 交互开发同时提供[简单代码编辑器](code-editor.md)：按项目 / 服务展示目录，多标签阅读与修改文本；画布与代码视图共享项目上下文，AI 候选修改经比较与审阅后应用。文件保存、Git 提交与部署分别处理，保护未保存内容并检测并发修改；完整 IDE 能力不作为首版前置条件。

## 核心概念

| 概念 | 定义 |
| --- | --- |
| 画布（Canvas） | 用户编排组件的可视工作区，同时是**一个真实项目空间**的期望态声明。一个画布对应一套 docker-compose（本机环境）/ k8s（规模化环境）项目空间。 |
| 项目空间（Project Space） | 画布声明的运行载体：一组相互关联的服务实例与中间件实例，拥有独立网络、卷与生命周期。 |
| 标准中间件（Standard Middleware） | 平台目录化提供的通用组件（MySQL、RabbitMQ、Redis、Kafka 等），有标准的参数面、健康检查与连接凭据模型。 |
| 服务组件（Service Component） | 由 AI 生成并维护的业务服务；声明输入契约、业务场景、依赖的中间件与对外接口。 |
| 服务代码仓库 | 每个业务服务配置的独立 Git 仓库，默认只在本地；首个切片即要求最小登记与固定 commit 追溯，完整 Git UI 后续。GitHub 可选，项目空间与仓库生命周期分开建模。 |
| 服务工程方案 | 为单个业务服务绑定的技术栈、运行环境与框架版本、规则集、模板及检查工具链；AI 与人工修改使用同一已解析方案，检查证据关联其版本。具体规则目录与支持矩阵尚未建立。 |
| 技术栈最佳实践文档包 | 每个受支持语言 / 框架 / 场景组合的工程主文档、适用通用规范、验证说明及版本清单；随服务仓库保存离线快照，由服务 `AGENTS.md` 引用，agents 开发前实际加载。缺少文档包的组合不能标为已支持。 |
| 草稿 / 部署目标 | 草稿是编辑与审阅中的候选画布版本；被接受为部署目标的版本才进入运行调和。保存草稿与接受部署目标分开，具体交互与状态机仍属待验证提案。 |
| 期望态 / 实际态 | 被接受为部署目标的画布及其组件声明构成**期望态**；项目空间内真实运行状况构成**实际态**。平台以调和（reconcile）方式持续收敛实际态到期望态，偏差显式呈现。这是「数字孪生」的一致性基础。 |
| 持久操作 | 接受目标时与元数据同库提交的待处理记录，保存阶段、外部资源、重试与恢复状态；平台重启后可接续，独立于浏览器和 SSE 连接。 |
| 共享中间件 / 项目中间件 | 中间件可以是全局共享实例（多个画布复用），也可以专属某个项目空间。归属在画布声明中显式建模。 |

## 关键不变量

以下不变量是平台一切实现与评审的最高判据，细化与阶段化见开发规范[开发工作流](../development/workflow.md)的状态与不变量矩阵。

1. **孪生一致性**：画布期望态与项目空间实际态的差异必须可观察、可解释；所有管理资源有明确归属，外部漂移不得隐匿或自动当作已接受目标，按授权调和与对账。
2. **零感知替换**：开放服务替换能力时，以业务流程不中断为验收目标，新版本健康就绪后才切流量，旧版本按序排空下线；失败恢复须核实实际版本及数据兼容。数据库 / 消息恢复与镜像回退分开设计，不承诺不兼容迁移也能一键回滚。
3. **声明原子性与执行最终一致性**：画布编辑在平台元数据库内整批提交；外部编排允许部分成功但须登记全部资源、失败和恢复入口，不留未登记的悬空资源，不要求跨 Git、数据库与 Docker 的完整事务。
4. **凭据隔离**：中间件连接凭据由平台按声明注入，不进入画布数据、不入前端、不落 AI 对话记录。
5. **AI 产物不豁免验证**：AI 生成的服务代码与模型变更必须通过与人工代码相同的测试与部署门禁，才可进入项目空间。
6. **配置生效语义显式**：每项服务配置必须声明生效模型（立即生效 / 需重启 / 需替换），平台按声明执行并如实回显。

## 目标架构（分层意向）

| 层 | 技术栈 | 职责 |
| --- | --- | --- |
| 前端画布 | TypeScript + React + React Flow | 画布编辑、组件目录、服务目录与多标签文本编辑、AI 对话入口、运行状态回显；画布是服务端期望态的投影，未保存文本只属编辑缓冲，不持有业务真相 |
| 平台服务 | Go | 画布与组件的领域模型、期望态存储、受控文件读写与 AI 变更协调、AI 编排（设计-开发-测试-部署流水线）、服务注册与配置管理、状态采集与调和 |
| 编排执行 | Go + docker-compose / k8s | 项目空间生命周期（创建、变更、替换、销毁）、零感知替换的流量切换与健康检查 |
| 元数据存储 | MySQL | 画布声明、组件目录、版本历史、部署目标、持久操作 / 事件及带采集时间的运行状态快照；凭据仅保存引用 |

服务端持有已提交的期望态，服务 Git 仓库保存源码版本；两者通过版本记录关联，不相互替代。一次部署需要记录画布版本、各服务仓库与不可变 commit、镜像 digest、测试及部署结果，详见[服务代码仓库与版本追溯](service-repositories.md)。

组件与连线使用[版本化领域契约](canvas-contracts.md)；[标准中间件](standard-middleware.md)由目录提供预定义、版本化的配置 / 端口 / 绑定 schema，业务服务保留各自的接口与多版本契约。平台接口与事件分别固定机器契约。部署以[持久操作与调和](operations-and-recovery.md)收敛，SSE 只通知与恢复投影；画布 revision、部署目标代次、操作版本和事件序号互不替代。

平台自身的 Go / TypeScript 技术栈与用户创建的业务服务技术栈分别管理。Java Web、TypeScript 等业务服务按各自的[服务工程方案](service-engineering.md)生成、修改与验证，不把平台语言、框架或工具版本直接套用于所有服务；通过格式检查也不等于架构、安全或业务行为已全部符合要求。

## 设计落地顺序

沿用[开发工作流](../development/workflow.md)的首个手写验证切片，以数据库版 Todo List 作为示例项目：单画布、MySQL、一个手写 Todo 服务、真实 compose 项目空间、数据持久化验证与状态回显。**该服务从首个切片就使用独立本地 Git 仓库，平台最小登记仓库身份、固定 commit、检查与镜像的关联；可先手工准备源码与提交，不能从变化中的工作区部署。** 该示例只用于验证，不成为平台内置业务或固定模板；用户已选择 Go + 标准库 `net/http`，对应文档包、模板与检查仍待工程方案切片交付。随后扩展完整 Git 管理 UI、简单代码编辑、AI 隔离工作区与变更审阅、零感知替换及配置生效能力；GitHub 不成为本机闭环前置条件。

首个切片同时验收仓库 / commit 追溯、标准 MySQL schema 与连接注入、数据库应用账号 / 迁移 / 就绪 / 应用入口、本机初始化与最小本地防护（平台账号认证仅保留未来边界，一期不开发或接入），以及持久操作幂等 / 重启恢复、数据库断连、部分成功、新目标替代旧任务和 SSE 恢复。首版停止、移除及项目删除默认保留源码 / 数据；物理清理能力在备份恢复就绪后再开放。所选业务栈的文档、最小模板与检查随该组合就绪，agents 实际加载在 AI 能力开放前验收；不要求先做全语言平台。备份恢复在开放升级、破坏性数据操作或真实业务数据前就绪。完整分阶段矩阵见[运行与恢复](operations-and-recovery.md#分阶段故障验收)。

完整工作台、完整 GitHub 接入与 AI 自动化均属于后续目标。视觉 token、布局尺寸和交互策略须在上述真实状态上验证，不以静态设计图证明运行能力。

## 边界与暂不承诺

- 本机环境以 **docker-compose** 为一等公民；k8s 是规模化方向，接口按可移植设计，不提前实现。
- AI 的自主边界：在已授权范围内提出组件与代码变更、在隔离工作区开发验证；本地提交、远端创建 / 推送、部署与数据迁移分别核对明确请求或已接受策略。默认自动提交 / 发布策略尚未决定，对**平台自身运行环境**的变更（升级平台、清空数据）不属于业务开发 AI 的自主权限。
- 多租户、对外 SaaS 化不在初期范围；先以单用户本机环境打通闭环。
