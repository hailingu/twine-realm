# 服务技术栈与工程规则设计

> **状态：首个 Go + net/http 工程包、离线引用核实与最小模板已实现；agents 自动加载与画布绑定仍为目标。** 已确认要求：每种受支持技术栈提供对应的工程最佳实践文档，agents 开发前实际加载，且每服务仓库 `AGENTS.md` 引用适用规范。工程方案、文档版本固定及离线可读为设计要求；首个组合、发布格式、模板与真实检查见 [Issue #10 工程模板切片](../development/service-profile-slice.md)。其他组合尚未建立，不把模板文件存在当作 agents 已实际读取。

## 目标与边界

每个业务服务选择自己的技术栈与工程方案，关联自己的[Git 仓库](service-repositories.md)。后续扩展为多业务服务时，订单服务可以选择 Java Web，发券服务可以选择 TypeScript 后端；二者各自采用适用的规则、模板和检查，不共享一份含糊的「最佳实践」提示词。

工程方案把语言习惯、框架约束、业务契约、验证与运维接口转成可追溯要求。AI 生成、AI 后续修改和人工开发使用同一方案；规则检查只能证明其声明范围内的结果，不能据格式化、插件通过或 AI 自评宣称安全、架构和业务行为全面合规。

平台自身的 Go / React / TypeScript 基线仍由现有[开发规范](../development/README.md)管理。业务服务单独解析技术栈，不直接继承平台的语言版本、React 约束或全部仓库工具配置；平台[核心不变量](README.md)仍约束生成与交付流程。

这种范围区分不免除项目规范要求：每个项目与每服务仓库 `AGENTS.md` 必须显式引用适用通用工程规范和技术栈最佳实践文档，agents 每次任务前实际读取。技术栈文档只补充项目规范，不能替代或降低其要求；来源与业务适用范围不明时按[规范上下文设计](ai-development-standards.md)阻塞，不擅自套用平台专属要求。

## 创建服务与版本选择

1. 用户拖入业务服务，在配置面板选择语言、运行场景与框架，如 Java Web、TypeScript 后端或 TypeScript 前端。这些是目标示例，不代表已支持的产品选项；标准中间件不进入业务源码生成流程。
2. 平台从受支持目录展示兼容的运行环境 / 框架版本与工程方案。主要版本供用户选择，其余模板、规则和工具链按方案解析，并可展开查看依据；不要求用户手填每个检查工具参数。
3. 服务端固化已解析方案，再在该服务的独立 Git 工作区中生成或修改项目。源码、配置与方案不一致时显式反馈，不能由前端或 AI 静默改写已接受配置。
4. 技术栈未选择、版本组合不兼容、规则有冲突或所需工具未准备好时，服务保持未就绪，说明原因与后续动作；不能降级成无检查项目后报告成功。

版本选择需记录精确解析结果与兼容矩阵，包括语言 / JDK 或 Node 等运行时、框架、构建 / 包管理工具、编译器和检查工具。默认可优先已经验证的受支持 LTS / 稳定系列，但不能只保存「最新」或「LTS」字样。依赖保留锁文件或等价解析记录；使用 BOM 时固定其版本并记录最终依赖解析结果，镜像基底也保留可追溯身份。

TypeScript 必须区分 Node、浏览器、测试及共享代码的运行条件，按环境确定模块解析与编译配置，不能把平台前端的配置直接复制给后端服务。新建与导入已有仓库均需先解析方案；已有结构和人工代码不因选择技术栈而被整仓覆盖。

## 可版本化的工程方案、规则集与模板

首个 Go 包已发布具体文件格式与 CLI；下表其余内容仍是逻辑记录，不代表已存在完整数据表或 API。

| 对象 | 应记录的内容 |
| --- | --- |
| 服务工程方案 | 标识、版本、内容摘要；适用语言 / 场景、受支持运行环境与框架组合，引用的规则集、模板与工具链 |
| 项目规范上下文 | 项目 / 服务仓库、根与路径级 `AGENTS.md`、其引用的软件工程规范及其他文档，来源版本、实际工作区摘要、适用范围与读取状态 |
| 技术栈最佳实践文档包 | 方案绑定的通用规范、技术栈 / 框架工程主文档、验证说明、来源清单与摘要；每个受支持组合均有可离线读取的不可变版本 |
| 规则集 | 标识、版本、内容摘要、来源版本 / 提交与条款定位、适用范围、冲突关系和检查方式 |
| 单条规则 | 稳定规则标识、意图、强制或建议级别、适用条件、自动检查映射或人工审阅要求、允许例外的边界 |
| 项目模板 | 标识、版本、内容摘要、兼容范围；源码骨架、实际构建与测试入口、工程配置、说明文档及必要运维接口 |
| 工具链 | 编译器、格式检查、静态分析、测试等工具的精确版本与配置摘要，实际执行环境与非交互入口 |
| 服务覆盖项 | 相对规则基线的显式调整、理由、作用范围与接受记录；不得使不可覆盖要求失效 |
| 例外记录 | 规则标识、受影响文件 / 符号、原因、补偿验证、审阅结论与复查 / 撤除条件；不作为全项目通用豁免 |

平台服务持有服务已接受的方案绑定；每个服务仓库保存对应版本快照、实际检查配置与可在本地执行的项目入口，供复现和人工开发使用。快照与服务端版本关联，不形成可独立写入的第二份期望态；手工调整配置先作为待审阅变更呈现。

规则集与模板应以不可变版本解析。在线指南地址只是来源入口，不能代替来源快照、版本 / 提交和内容摘要。上游指南或工具发布新版本时，不静默改变正在开发的服务；升级形成独立变更，列出新增 / 删除规则、兼容影响及需重做的检查。模板版本表示来源，最终仍验证实际源码与配置，不能仅凭「由模板生成」判断符合要求。

## 每种受支持技术栈的工程最佳实践文档

「受支持技术栈」按语言、框架、运行场景与兼容版本组合定义。Java Web、TypeScript Node 后端、TypeScript React 前端属于不同组合，不能只发一份语言风格文档就声称框架工程要求齐备。用户已选择首个业务组合为 Go + 标准库 `net/http`；相应首个支持包见上述切片。以下要求继续约束后续组合，不表示其他技术栈已支持。

| 文档组成 | 必须说明的工程内容 |
| --- | --- |
| 通用工程规范 | 职责与依赖、可维护性、状态 / 失败 / 资源清理、注释与审阅、行为测试、例外机制；逐项标明业务通用条款，不混入平台专属目录与命令 |
| 技术栈最佳实践主文档 | 适用语言 / 运行环境 / 框架版本、布局与模块、依赖管理、配置、输入校验与授权、错误 / 超时 / 取消、并发与事务、迁移、日志 / 健康 / 停机及对应测试策略 |
| 场景补充 | 如 TypeScript 的 Node / 浏览器 / React 边界、Java Web 所选框架约束、数据库与消息的幂等及恢复；只加载实际适用部分 |
| 验证说明 | 真实工作目录、非交互构建 / 类型 / 静态 / 测试入口、检查覆盖范围与人工项、环境准备、未支持能力；不虚构已安装工具或检查命令 |
| 版本与来源清单 | 包标识和版本、适用组合、来源版本 / commit、逐文档摘要、适用条款与路径、规则 / 模板 / 工具链绑定及例外；推荐以随包的机器可读清单固定 |

工程文档采用平台受控发布的适用版本，原规范保留来源；平台专属要求不自动发布给业务项目，业务项目自己的约定与覆盖项另外记录。现有 `docs/development/` 继续只约束平台开发，不通过本文修改其原始适用范围；未来抽取可复用通用条款时需逐项映射和评审，不能整目录盲拷贝。

文档包与模板同时交付，版本不可原地改义。服务仓库保存完整可读快照、来源清单与适用配置，独立 clone 或 worktree 检出后可离线读取；不能仅挂载平台开发机上的绝对路径或依赖实时网页。推荐在服务 `docs/engineering/` 中保存入口、通用规范、技术栈主文档与验证说明，具体目录和清单 schema 随首次发布固定，`AGENTS.md` 使用仓库内相对引用。

服务根 `AGENTS.md` 必须列出实际适用文档、版本定位与路径范围，并要求 agents 开发前读取。自动执行器先校验引用、实际内容和兼容组合，再将原文按范围纳入任务上下文；任务记录每份文档版本 / digest、加载结果与验证映射。不能只生成 AGENTS.md 后假定外部 agents 会自觉读取；通过平台启动的所有 agents 入口都执行同一前置检查，平台外执行无法核实的读取不报告为已验证。

一个组合只有在文档包、模板、检查入口与最小构建 / 运行验证都具备后，才能标为「受支持」。只有在线参考、没有对应框架规则或检查不可运行的组合显示为未支持 / 待就绪，不降级成无规范生成。文档离线可读不等于依赖、镜像和 AI 已支持完整离线运行。

## 模板与最小交付物

首个具体技术栈先交付一个能在干净环境按文档运行的模板，再逐个扩展；不以建立全语言规则平台为前置。模板至少包含源码骨架、依赖锁定或等价解析记录、脱敏配置示例、所需迁移文件、行为测试、实际构建入口、健康 / 就绪与优雅停机约定、README、服务 `AGENTS.md` 及适用工程文档快照。没有数据库的服务不强加数据库迁移能力。

模板示例业务不能硬编码为所有用户项目的 Todo，源码与配置按实际服务需求生成。构建记录关联源码 commit、模板 / 工程文档 / 工具链版本、依赖与镜像基底身份、输出镜像 digest 和迁移版本；检查后变更源码或配置，重做受影响检查，部署使用已验证的同一不可变产物。

## 模板必须实现的运行契约

模板除工程文档和检查外，还须声明并实现[服务运行契约](standard-middleware.md)：消费端口及绑定格式、容器 HTTP 端口与访问入口、配置 / 凭据文件读取、迁移命令 / 历史 / 锁、启动 / 就绪 / 存活探针、停机信号及超时。非敏感注入名与秘密文件约定要在所选框架中真实验证，不能只有 schema 而没有可运行的消费实现。

首个 Todo 示例按用户选定的 Go + 标准库 `net/http` 提供对应最小模板、可离线工程文档与真实检查，再开放该受支持组合；agents 实际读取在 AI 入口开放前验收。首个手写服务同样登记独立本地 Git 与固定 commit，不依赖完整 Git UI。具体兼容版本、文档清单和模板在工程方案切片锁定并验证，不将 Todo 固化为产品内置业务。

## Java Web 与 TypeScript 的参考范围

以下是候选规则来源。实际采用时还需固定版本、选择条目并验证工具覆盖；本轮没有建立或启用任何规则包。

| 来源 | 可采用的范围 | 适配边界 |
| --- | --- | --- |
| [Google Java Style Guide](https://google.github.io/styleguide/javaguide.html) | Java 源文件组织、格式、命名与可明确检查的编码约定 | 作为可选择的代码风格基线；不据此推导完整 Web 安全或系统架构要求 |
| [Alibaba Java Coding Guidelines / P3C](https://github.com/alibaba/p3c) | 按选定指南版本抽取适用编码与工程规则，记录严重性和条款来源 | PMD / IDE 插件只覆盖所实现的规则；未覆盖项独立审阅，不能把插件通过解释为整本指南全部合规 |
| [TypeScript strict](https://www.typescriptlang.org/tsconfig/strict.html) | 严格类型检查作为新服务的候选默认基线 | 固定 TypeScript 版本、实际开关与覆盖范围；编译器升级可能带来新诊断，需单独验证 |
| [TypeScript 环境与模块配置](https://www.typescriptlang.org/docs/handbook/modules/guides/choosing-compiler-options.html) | 按实际运行环境 / 构建器选择编译与模块解析配置 | 后端、浏览器、测试等按适用范围配置，不把所有环境混成一个无差别模板 |
| [TypeScript 类型断言说明](https://www.typescriptlang.org/docs/handbook/2/everyday-types.html) | 区分编译期类型与运行时数据 | 类型断言不会验证运行时输入；HTTP、消息、配置等边界仍需独立校验与行为测试 |
| [typescript-eslint 配置](https://typescript-eslint.io/users/configs/) | 选择适用的推荐或类型感知规则，配套真实类型信息与版本 | 按项目裁剪并解析冲突，固定配置和工具版本；不能以无差别启用所有规则代替规则设计，格式化另有明确基线 |
| [OWASP ASVS](https://asvs.owasp.org/) | 为 Web 服务单独定义可验证的安全需求 | 明确采用的标准版本、条款和验证方法；不能因通过风格检查就报告安全符合要求 |
| [Spring Boot 测试文档](https://docs.spring.io/spring-boot/reference/testing/index.html) | 选择 Spring Boot 时，按对应框架版本定义测试支持与适用测试层次 | 只适用于所选框架及版本；业务契约、事务与真实依赖验证仍需按服务场景设计 |

Java Web 选择 Google 或 Alibaba 风格时，必须明确一个格式基线。其他来源的规则可经适配后补充，但格式、命名等冲突不能简单叠加或让不同格式工具反复改写同一文件。Java Web 的输入校验、鉴权、事务、迁移、超时、日志、健康与停机等要求按实际架构单独定义；不靠代码风格指南代替这些设计。

TypeScript 工程方案拟将严格类型检查、适用的类型感知 lint、依赖边界、Promise / 错误处理、输入的运行时校验及行为测试分别记录。检查范围包含适用源码与测试；排除项、降低检查强度或加入抑制标记都属于可审阅的规则变化。

## 冲突优先级与例外

1. 平台核心不变量、凭据隔离与交付硬性要求不可被模板、服务覆盖项或 AI 指令豁免。
2. 已接受的项目 / 路径级规范、业务契约、所选运行环境 / 框架的兼容性与强制工程规则需要同时满足；冲突无法解决时返回阻塞原因，不能用覆盖顺序掩盖互斥条件。
3. 在项目规范允许覆盖的边界内，显式接受的服务覆盖项优先于选定规则集的可覆盖默认；规则集优先于模板默认。技术栈通用规则不能替代已有项目规范。允许例外的规则按记录审阅，强制与建议级别不得由 AI 临时更改。
4. 同层来源冲突时，采用服务中已明确选择的基线；未选择或无法解析时先处理冲突，再生成或修改项目。AI 建议与工具自动修复都不能自行决定新的规则优先级。

例外与存量问题需按规则范围定位。已有仓库可以先建立真实基线与迁移计划，但不能把历史问题或未运行项改记为通过，也不能用存量例外普遍豁免新增代码。

## 生成、人工修改与检查流程

1. **解析上下文**：先解析服务已接受的技术栈方案与文档包身份，再完成项目及服务 `AGENTS.md` 的规范引用校验、适用通用 / 技术栈 / 项目文档的实际读取，记录固定版本、工作区摘要和条款 / 验证映射；同时核对画布、仓库基准、模板、规则集、覆盖项和工具链。规范未就绪时不进入下一阶段。
2. **在隔离工作区修改**：生成真实可构建项目，或以差异修改已有源码和工程配置；保持人工改动，冲突显式呈现。AI 开发任务使用本次已解析规则，不能只在对话中口头承诺遵循指南。
3. **执行同一检查**：AI 与人工修改采用同一规则和入口，本地 Git 与 GitHub 两种仓库接入不改变标准。工具在受控工作区执行；不能以未经接受的测试删除、源码排除、规则降级或检查配置替换绕过失败。
4. **审阅与反馈**：展示自动检查范围、失败定位、未运行项、工具错误、待人工判断项及例外；AI 可提出修复或审阅建议，但自评不能冒充人工结论。
5. **固化证据与交付**：检查和审阅绑定实际源码 commit、项目规范集合、工程配置及环境，关联镜像与部署记录。交付前再次核对规范内容与引用；源码、规范、规则、覆盖项或工具链变化时，按影响范围重做检查，不能沿用其他版本的通过结论；部署仍遵守已有门禁与授权策略。

## 自动化范围与人工判断

| 关注点 | 可自动验证的方向 | 仍需单独判断的部分 |
| --- | --- | --- |
| 格式与编码规则 | 已选格式基线、导入 / 命名等可静态判断条目的规则映射 | 工具未覆盖条款、规则冲突、例外是否合理 |
| 编译与类型 | Java 编译、TypeScript 类型检查、适用类型感知规则与构建 | 编译成功不能证明业务语义或运行时输入合法 |
| 架构与依赖 | 明确配置的依赖边界、循环依赖、版本解析与静态分析 | 职责划分、领域模型、事务边界和架构取舍是否适合业务 |
| 业务与集成 | 对已声明场景执行单测、契约与真实依赖边界测试 | 场景是否充分、并发 / 幂等与失败恢复证据是否可信；不能用 mock 调用次数代替 |
| Web 安全与运行行为 | 对选定条款执行输入、权限、敏感信息、健康与生命周期等检查 | 威胁假设、授权语义、数据迁移与上线影响；单个扫描器不能覆盖全部要求 |

每项检查分别保存「通过 / 失败 / 未运行 / 工具错误 / 不适用」与适用原因；人工项保留待审阅、已判断或已接受例外的独立结果。规则集规定哪些是阻塞项、哪些是建议项；要求执行的检查未通过、必需人工项未处理或存在未接受的规则调整时，不进入部署。不能把工具无法运行、没有匹配源码或缺少类型信息当作检查通过。

## 后续验证与落地范围

下列是未来验收方向，本次未执行产品功能验证。

| 场景 | 应观察到的结果 |
| --- | --- |
| 同画布创建 Java Web 与 TypeScript 服务 | 各自绑定技术栈、版本与独立 Git，工程方案不会串用 |
| Google 与 Alibaba 风格规则发生冲突 | 按已选格式基线解析；未明确选择时返回冲突，不循环改写代码 |
| TS 类型通过但外部输入不符合契约 | 运行时校验 / 行为测试显式失败，不把类型断言当作输入验证 |
| 人工或 AI 修改已有服务 | 使用同一规则版本与门禁，不覆盖无关人工改动，不关闭检查绕过失败 |
| 检查工具不可用或必需人工项待审阅 | 显示真实原因并阻止进入部署，当前运行版本仍可追溯 |
| 升级框架、规则集或模板 | 形成差异与兼容评估，重做受影响检查；历史部署仍关联原版本 |
| 所选技术栈缺少最佳实践文档或服务入口未引用 | 组合未就绪，指出缺项，不进入 AI 软件开发 |
| 独立检出服务仓库且无法访问规范源网站 | 从版本匹配的仓库内快照加载原文并记录结果，不要求连接平台开发机 |
| 执行中上游发布新规范，或服务主动更改绑定 | 上游发布不改变当前任务快照；主动更改绑定使上下文过期并重校验 |

每种受支持组合必须配套文档、服务 AGENTS 引用、不可变离线快照与加载记录，这些原则已确认；首批组合已确认为 Go + 标准库 `net/http`；服务支持目录、文档包 schema、规则条目与工具映射、发布工具、例外细节和结果契约仍需实现细化。以数据库版 Todo List 示例项目（手写 Todo 服务与 MySQL）作为首个真实纵向验证切片，先在一个具体服务栈中验证相应规则与检查，再逐片固化工程方案。Todo 仅用于演示和验证，工程规则与模板仍按服务技术栈和真实业务需求选定；本设计不要求先建立覆盖所有语言的规则平台。当前仓库的工具门禁不等同于业务服务门禁，具体接入需在实现时登记并提供真实执行证据。
