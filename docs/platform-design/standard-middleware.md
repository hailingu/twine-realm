# 标准中间件 Schema 与服务运行契约

> **状态：MySQL 1.0.0 配置 / 端口目录与草稿、v2 服务自有契约和依赖声明已实现；运行仍为设计。** 2026-11-04 用户明确标准中间件可以提供 schema；本设计将其固定为目录内预定义、版本化、可校验的契约。已发布字段和边界见[组件目录](../development/component-catalog-slice.md)与[服务依赖声明](../development/service-bindings-slice.md)。以下运行 / 注入方案、相关数值仍属于首版建议，待真实适配验证后发布，不表示已创建业务数据库或凭据。

## Schema 的范围与所有者

标准中间件由平台目录提供确定的定义包。配置表单、具名端口、连接校验、部署计划和适配器解析同一包版本，不让 AI 每次临时猜测中间件如何使用；不直接把上游任意配置文件当平台契约。

| 契约 | 定义与验证内容 | 权威所有者 |
| --- | --- | --- |
| 定义包清单 | 组件定义 ID / 不可变版本、内容摘要、支持的镜像与协议系列、schema 引用、能力与运行适配版本 | 平台中间件目录 |
| 组件配置 schema | 非敏感参数的类型、必需项、范围、枚举、可选项及默认解析规则；凭据仅允许引用 | 对应中间件定义包 |
| 端口定义 | 稳定端口 ID、提供 / 消费角色、协议及版本、基数、必需性和连接契约引用 | 中间件或服务的固定定义版本 |
| 连接绑定 schema | 该关系的数据库名 / 命名空间、读写用途、所需能力、凭据引用和允许的注入模式 | 关系契约与两端定义包 |
| 运行能力描述 | 健康探针、配置生效模型、生命周期操作、镜像 / 持久卷 / 网络映射和适配器支持范围 | 受信目录与运行适配器 |
| 业务数据库 schema | 服务自己的表、索引与数据迁移；与中间件的配置 schema 不同 | 对应服务 Git 仓库中的迁移文件 |

业务服务按所选工程方案声明所需端口、配置与接口契约；自定义服务可有多种协议、多个版本和可选能力，不强制所有服务共享单一固定 schema。用户定义的服务契约经过登记、版本绑定和服务端校验后才可连线，不能仅以「自定义」绕过兼容检查。首个切片只需 MySQL 与手写服务的一组确定定义，不要求先实现通用插件市场。

## 发布、引用与兼容规则

1. 标准中间件包随平台支持目录发布，保存定义版本、各 schema 身份 / 摘要、镜像兼容范围及运行适配版本。推荐配置和连接参数采用 [JSON Schema 2020-12](https://json-schema.org/draft/2020-12/json-schema-core)；具体 Go / TypeScript 校验工具在实现时选择并验证实际支持的方言。
2. 引用只解析登记包内或已允许的依赖包，离线可读取；不按用户输入的 `$ref` 任意联网或读取宿主文件。定义包不是可任意执行脚本的权限来源。
3. 配置对象明确必需字段和扩展策略，首版推荐拒绝未声明字段。可选字段缺省值由服务端规范化并写入回执，不能假定 JSON Schema 的 `default` 注解会自动修改输入。只读计算值与用户可写字段分别定义，真实地址由运行观测产生。
4. 实例固定定义版本；连线固定两端端口与适用关系契约。添加字段、改变默认、生效模型、权限或协议均评审兼容影响；不原地改义。升级先生成迁移后候选图，再整体校验、审阅和接受，不静默升级既有实例。
5. JSON 结构合法只是第一层。服务端还须检查端点角色、协议 / 能力、基数、引用、归属、配置组合和启动依赖；业务输入 / 输出 schema 的兼容不能简化为两个对象都能通过自己的校验器。首版仅接受目录明确登记的兼容组合，未知组合拒绝并说明原因。
6. 草稿可以缺少部署所需值，但已填写值仍须合法，错误和未就绪项可定位。部署前补齐必需值、凭据与运行依赖。未知定义 / schema 版本保留原输入并拒绝使用，不丢弃字段后继续。

前端读取相同 schema 做表单和即时预检，服务端做最终判断；agents 使用相同定义提出候选变更。图编辑仍经[领域事务](canvas-contracts.md#原子编辑幂等与补偿)整批接受，schema 不授予创建容器、安装依赖或执行迁移的权限。

## 首个 MySQL 定义与连接

配置、标准提供端口和服务依赖声明已按上述切片发布；下表中的运行、注入和应用入口仍是后续机器契约的建议，不将声明当作运行事实。

| 对象 | 首版建议内容与边界 |
| --- | --- |
| MySQL 配置 | 引用受支持镜像 / 运行方案；字符集、排序规则等受控枚举；卷声明与资源限制；默认项目专属、数据持久化，业务库不发布宿主端口 |
| MySQL 端口 `mysql` | 提供 MySQL 协议连接，可绑定多个已授权服务；不据多条连接开放全库权限。实例版本与适配器须在目录兼容矩阵中 |
| 服务端口 `database` | 消费匹配的 MySQL 能力；首个示例为必需、最多一个绑定。其他服务按自己的定义决定名称、数量与必需性 |
| 数据库依赖关系 | 消费服务 → 提供 MySQL，记录稳定绑定 ID、两端端口、数据库身份 / 名称、用途、绑定契约版本与凭据引用；箭头表示依赖，不表示数据库返回数据的流向 |
| 数据库身份 | 推荐每服务使用独立数据库与独立应用账号；名字按不可变资源身份生成或验证，显示名变更不重建库。跨服务共享表结构不作为隐含默认 |
| 注入方案 | 非敏感 `DB_HOST`、`DB_PORT`、`DB_NAME`、`DB_USER` 和 `DB_PASSWORD_FILE`；密码内容仅在受限文件中供运行实例读取。具体名称随所选模板验证，不能假定任意框架天然支持 |
| 服务运行入口 | 固定容器监听端口、HTTP 入口及进程信号约定；模板声明启动、就绪与存活探针。首个 Todo 建议由同一业务服务提供简单页面与 API，仍只有服务与 MySQL 两个画布组件；用户已选 Go + 标准库 `net/http`，具体页面实现在工程方案 / 示例切片验证 |

`DB_HOST` 使用项目网络中稳定的运行地址，不把容器 IP 写成用户配置。凭据值不进入画布、部署清单、代码、构建参数、AI 上下文或 SSE；清单只保存用途与引用版本，构建不接触运行数据库秘密。模板负责从文件读取并交给对应框架，日志禁止输出连接串。

推荐 macOS 执行器从系统凭据库取值，按用途生成工作区之外的受限运行凭据文件，再由受信 Compose 适配器只读挂载到获准容器；文件名 / 容器路径可记录，内容不能进入普通元数据。文件权限与宿主目录隔离须验证。普通 Compose 的文件型 secrets 是文件挂载，不等于额外的加密存储；活动容器仍依赖的文件不能过早删除，停止后按引用清理。磁盘临时材料和本机 Docker 管理员是明确的信任边界，若安全策略不允许落地此类文件，应阻塞该注入方案并选择经过验证的适配器，不能静默退回明文环境文件。[Docker Compose secrets](https://docs.docker.com/compose/how-tos/use-secrets/)

## 初始化、账号与迁移责任

| 责任 | 执行者与权限 | 持久结果与恢复 |
| --- | --- | --- |
| MySQL 首次初始化 | 受信适配器使用专用管理凭据初始化新实例；管理凭据不交给业务服务、构建或 agents | 登记实例 / 卷身份及初始化状态；已有卷先核实版本和凭据，不能按空库重新初始化 |
| 建库与建账号 | 按绑定生成确定的数据库与账号身份；管理适配器执行受控操作，不接受任意用户 SQL | 验证已存在对象的归属和权限后接续；同名但归属不符时阻塞，不覆盖或接管 |
| 运行账号 | 仅允许该服务声明的业务库与 DML 权限，无全局管理、授权或 DDL 权限 | 凭据引用与授权结果登记；权限变化形成可审阅的绑定变更 |
| 迁移账号与执行器 | 单独的临时迁移任务使用目标库内必要 DDL / 数据迁移权限；不把管理权限传给应用常驻进程 | 关联服务 commit、迁移文件摘要 / 版本、数据库身份与执行结果；账号 / 许可只在任务需要时提供 |
| 迁移文件 | 由服务仓库版本化，适用工具与实际入口随技术栈方案发布；不使用平台元数据的迁移历史表 | 一库一次迁移，使用所选迁移工具的数据库锁和可核实历史；对已应用迁移的内容变化拒绝或进入人工处理 |

业务迁移脚本属于待验证代码，在限制路径、网络和凭据的迁移执行环境运行。跨项目的建库、授权和卷操作只能由受信适配器执行。不能用「启动容器时的初始化脚本会重复执行」假设处理已有数据卷。

MySQL DDL 不按跨步骤可整体回滚设计；迁移中断、连接丢失或未知结果先核对迁移历史和实际表结构，不能只因客户端超时就重跑。无法判断完整性时标记需人工处理，保留原库与证据；不自动清 dirty 状态、改迁移版本或回滚业务数据。新目标 / 取消也须等待或核实已经发出的迁移动作，不并发启动另一套迁移。

## 从连线到可访问应用

1. 保存合法草稿，登记独立服务仓库、固定源码 commit 与工程方案；检查并构建候选产物。构建或规范未就绪不能接受为可部署清单。
2. 审阅固定画布版本、各服务 commit / 镜像 digest、MySQL 定义版本与卷身份、绑定、迁移计划和检查证据；接受后在平台元数据库同事务保存目标、操作及事件。
3. 在每项目资源写入串行边界内，核实 / 创建网络、卷与 MySQL；数据库可认证执行检查后再准备数据库、账号与权限。每步登记资源身份和原操作，结果未知先查询。
4. 执行所绑定服务 commit 的迁移；成功后才按固定镜像与配置启动业务服务。迁移失败时不启动待部署的新版本，也不删除数据库或报告整个项目成功。
5. 服务就绪检查验证所需配置、数据库连接和迁移前提；存活检查只验证进程可响应，不把数据库暂时不可用直接等同必须循环重启。探针应限时、无业务写入且不输出秘密。
6. 发布并核实应用入口：首版建议服务容器端口映射到 `127.0.0.1` 的固定已登记宿主端口；冲突时阻塞并由用户改配置，不静默换地址。平台页面展示独立的应用链接，不将业务 HTML 代理到控制台同源路径。业务库仅在项目网络可访问，调试暴露是另一个授权动作。
7. 容器就绪、实际镜像 / 配置与目标相符，并经已发布入口完成无副作用检查后，操作才成功。示例验收另外执行新增、列表、完成和删除，重启后验证数据仍在；创建请求结果未知时以示例约定的请求键 / 已返回记录身份核实，不能盲目新增。

首个业务组合已确定为 Go + 标准库 `net/http`；相应切片应发布上述运行 / 绑定契约、健康路径、迁移入口及 Todo API 的实际请求样例。具体兼容版本在对应工程方案中锁定验证；API 的具体字段和幂等语义须在示例实现前固定并验证。

## 配置变化与验收

连接信息、数据库账号、卷身份、字符集 / 排序规则和镜像版本等分别声明生效模型与修改限制。首版连接绑定变化建议需重建运行实例；已有库的字符集、名称或数据迁移不可用普通表单修改伪装成热生效。删除连线或组件只改变声明，停止 / 保留数据仍遵守[资源生命周期](operations-and-recovery.md#停止移除与删除)。

| 场景 | 必须观察到的结果 |
| --- | --- |
| MySQL 配置越界、未知字段或定义版本 | 服务端明确拒绝，图与旧配置不变；前端与服务端按同包反馈 |
| 不兼容协议、错误端口、缺必需绑定或超基数 | 编辑非法关系被拒绝；未完成草稿可保存且显示阻塞原因，部署不可接受 |
| 合法连线与首次部署 | 无须修改源码内连接信息，最小权限账号可完成业务操作，管理凭据不可见 |
| 已有卷、账号创建成功但响应丢失 | 查询并核实原对象，不重复建库、不重置密码、不覆盖他人数据库 |
| 迁移失败或结果未知后重启平台 | 记录对应源码与库状态，核实后接续或人工处理，不自动清库或盲重跑 |
| 数据库断连、服务就绪失败或宿主端口冲突 | 具体原因与实际入口可查，不误报成功、不误连其他服务 |
| schema 升级与凭据轮换 | 原版本仍可追溯；升级 / 重新注入单独记录，旧任务不能覆盖新绑定 |

已发布 MySQL 1.0.0 离线配置 / 端口包及 v2 服务依赖声明，具体边界见[组件目录](../development/component-catalog-slice.md)与[服务连线](../development/service-bindings-slice.md)。真实运行、账号与注入适配仍待后续；其他标准中间件按相同发布规则增加各自的配置、端口和连接契约，不因设计中出现名称就视为已支持。
